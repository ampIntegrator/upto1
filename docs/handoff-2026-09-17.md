## How the project works

- **Three layers.** `src/fields/sections/` is the neutral section builder (future Payload
  plugin: grid, rows, columns, mobile order, drag and drop, validation). It knows no
  component, no theme, no media collection and never imports `src/components/`. The site's
  choices live in `src/sections.config.ts` (section settings, block list, row condition)
  and `src/fields/blocks/` (one `ContentBlock = {block, minSpan, maxSpan?, fill?}` per
  block). Rendering: `src/lib/sections.ts` (Payload data → props, async) and
  `src/components/PageSections.tsx` (Astryx components).
- **Branches.** Components and catalogue on `astryx`, back-office and blocks on `payload`,
  pull requests to `main`. Nicolas does not use git: do the branches, then give him the two
  compare links (`main...astryx`, then `main...payload`, in that order because `payload`
  contains `astryx`). Sync with fast-forward merges: commit on `astryx`, then
  `git checkout payload && git merge --ff-only astryx`.
- **Language.** Talk to Nicolas in French (tutoiement). Code comments, commits, docs in
  English. Admin texts in FR and EN dictionaries (`src/i18n/admin/*.ts`), never hard-coded.
- **`consignes.md`** is Nicolas's scratch file: read it when he says so, never write in it
  unless he explicitly asks for that file. A Monitor on its modification time is how he
  hands over instructions; re-arm it every 30 minutes.
- **Database.** Never `push`. For any field change: `pnpm run db:backup`, then
  `pnpm run migrate:create <name>`, read the generated file (only the expected CREATE /
  ALTER / DROP), `pnpm run migrate`, `pnpm run generate:types`. When a change both drops
  and creates tables, drizzle asks an interactive question and the command hangs: split into
  two migrations (add first, drop second). Check the schema is in sync with
  `pnpm payload migrate:create check --skip-empty` (it must create nothing).
- **Never delete a document someone may have open in the admin** (a seed that recreates demo
  content): the edit view of a deleted document reloads in a loop with its live preview and
  locks the SQLite database for every writer (22 September 2026). Seeds update in place.
- **Tests.** Never on a real page. `pnpm smoke:sections` (dev server running) creates a
  throwaway page with every block, checks the width rules and the site rendering, then
  deletes it: extend it with every new block. `pnpm test:int`, `pnpm run lint` (0 errors),
  `pnpm exec tsc --noEmit`. `pnpm seed:demo` recreates the three demo pages
  (`/demo-tarifs`, `/demo-contenus`, `/demo-etapes`): add the new blocks there too.
- **Picker previews.** `PREVIEW_SLUGS` in `src/fields/blocks/previews.ts`, one demo per
  slug in `src/app/(frontend)/apercu/[slug]/Apercu.tsx`, then `pnpm previews:build`.
- **Known traps.** A block file that imports `@payloadcms/richtext-lexical` (server) must
  never be imported by client code: keep its slug in a separate module (see
  `textBoxSlug.ts`), otherwise Next fails with « Can't resolve 'fs' ». Payload's database
  adapter reads `admin.condition` on array / block / group fields to make required columns
  nullable: do not remove the `condition` of the `rows` field. The dev server (started by
  Nicolas) sometimes keeps a stale server render for a catalogue route after a component
  change: a hydration error on one `/design/composants/*` route only means restart
  `pnpm dev`, not a bug.
- **Titles.** Every title field comes with the shared `tagField` (h2 to h6, p or span) and
  the component renders it through `Title` (`src/components/TitleTag.tsx`): the tag never
  changes the look.
- **Widths.** Minimum and maximum spans come from the catalogue's registry,
  `src/components/content-specs.ts` (`minSpan`, `maxSpan`, capacity tables such as
  `stepsCapacity`), tested in `tests/int/content-specs.int.spec.ts`. A block whose
  capacity depends on its data validates its own field against `columnSpanAt(data, path)`
  with an explicit FR/EN message (see `processStepsBlock.ts`, `collectionBlock.ts`).

## Work item 1: Tabs (« Onglets »)

Decisions: a column of **6 to 12**; each tab has a label of **50 characters at most** and
a rich text (same restricted Lexical editor as the text box: paragraphs, bold, italic,
links, bulleted and numbered lists; no button). **Cap on the number of tabs by column
width: 4 on 6 or 7 columns, 6 on 8 or 9, 8 on 12**; the tab strip still scrolls when the
labels are wider than the strip (Astryx TabList, `overflow="scroll"`), on mobile too.
Tab labels are buttons, not titles: no tag field. The block fills the row height.

Branch `astryx`:
- `src/components/Tabs.tsx` + `.module.css`: house component on Astryx `TabList` / `Tab`
  (already dressed by the theme; `role="tablist"` with panels) and `RichText` for the
  content. Props: `items: {label: string; content: RichTextDocument | ReactNode}[]`,
  `defaultIndex?`, `label?` (accessible name). Keyboard and ARIA come from Astryx.
- Registry: `{type: 'tabs'; count: number}` with `tabsCapacity(span)` (6–7 → 4, 8–9 → 6,
  12 → 8) and `minSpan` 6, `maxSpan` 12. Update the `tabs` entry (today `minSpan: 6`).
- Showcase `TabsShowcase.tsx` (add `Tabs` to `scripts/gen-catalog.mjs` in
  `conteneurs`, OWN and DRESSED, then `pnpm catalog:build`), Grille page samples, tests.

Branch `payload`:
- `src/fields/blocks/tabsBlock.ts` (+ `tabsSlug.ts`): `items` array (minRows 2, `label`
  text localized required with `maxLength: 50`, `content` richText with `textBoxEditor`
  from `textBoxBlock.ts`); validation of the count against `tabsCapacity(columnSpanAt(...))`
  with a FR/EN message; `ContentBlock` `{minSpan: 6, maxSpan: 12, fill: true}`.
- Dictionary `tabsBlockText` in `src/i18n/admin/blocks.ts`; add to `sections.config.ts`;
  conversion in `lib/sections.ts` (`{type: 'tabs'; tabs: {...}}`), rendering in
  `PageSections.tsx`; preview; migration; smoke test; demo page; docs table.

## Work item 2: Button group (« Groupe de boutons »)

Decisions: a column of **6 to 12** (7 accepted, same capacity as 6). Two modes:
- **Attached** (« collés »): the buttons form one connected control, on Astryx
  `ButtonGroup`. **Split buttons may be attached too**: try it, show Nicolas a capture, and
  fall back to « attached = simple buttons only » if the result is unreadable.
- **Spaced in columns** (« espacés »): 2, 3 or 4 inner columns, one button each, the gap
  being the section's column gap (`var(--section-gap-x)`, set by `PageSections`).
  Capacity by width like the steps: 2 columns on 6 or 7, 3 on 8 or 9, 4 on 12. Per group,
  a width choice: **natural** (each button keeps its width, aligned left / centre / right in
  its column) or **full** (each button fills its column, arrow at the edge, like `block`).
Each button: the text box's settings (label, href, shape simple or split, variant primary /
high / secondary / ghost, size md or lg, optional Nucleo icon on simple buttons). Group
alignment left / centre / right. Below 640 px the buttons stack.

Branch `astryx`:
- `src/components/ButtonGroup.tsx` + `.module.css`: house component; attached mode on
  Astryx `ButtonGroup` with our `Button` (split included: check the cells and frames of
  `Button.module.css`); spaced mode as a grid `repeat(n, minmax(0, 1fr))` with
  `gap: var(--section-gap-x, 24px)`, stacking below 640 px (container query on the
  column). Props: `mode`, `columns`, `width`, `align`, `buttons: TextBoxButton[]`
  (reuse the type from `TextBox.tsx`).
- Registry: `{type: 'buttonGroup'; columns: 1 | 2 | 3 | 4}`, `buttonsCapacity(span)`,
  `minSpan` 6, `maxSpan` 12. Showcase, catalogue (`actions`), tests.

Branch `payload`:
- `src/fields/blocks/buttonGroupBlock.ts`: `mode` select, `columns` select (validated
  against the capacity), `width` select, `align` select, `buttons` array (the same rows as
  the text box's buttons: extract them into `src/fields/blocks/buttonFields.ts` and reuse
  in both blocks), at most 4 buttons and, in spaced mode, exactly one per column.
- Dictionary, config, conversion, rendering, preview, migration, smoke, demo, docs.

## Work item 3: Row layouts

Decisions:
- **Add the 8·2·2 layout** (fifteen layouts): columns are reordered by dragging, so 2·8·2
  (a centred 66 % column) comes from it; the FAQ (max 9) fits in the 8. Add
  `[8, 2, 2]` to `ROW_PRESETS` in `src/fields/sections/grid.ts` and its test in
  `tests/int/grid.int.spec.ts`. An image already fits a column of 2 (`mediaBlock`
  minSpan 2): nothing to do.
- **A « Carousel » thumbnail**: a second full-width tile that creates the row of 12 with
  the Collection block already placed in its column (layout « swipe » by default; the
  editor switches to carousel inside the block). No new data: a column has no « kind »,
  the block decides. The classic 12 tile stays for image, image with quote, steps and
  tabs. In `RowsBuilder.tsx`, `addRow` adds the row and its column with `addFieldRow`;
  adding the block means one more `addFieldRow` on `${path}.${index}.columns.0.contents`
  with `subFieldState` `{blockType: {value: 'collection'}}` (check Payload's blocks field
  state shape by reading how `dispatchFields` / `addFieldRow` builds a block row; the
  core must not know the slug: pass it through the builder's options, for instance
  `presetBlocks: {carousel: 'collection'}` in `createSectionBuilder`, and keep
  `src/fields/sections/` free of site slugs).
- **Values inside the thumbnails**: each cell of a layout tile shows its width (2, 3, 4…
  12) centred horizontally and vertically (`Tile` in `RowsBuilder.tsx`, 40 px high, text
  14 px, Payload theme colours); the carousel tile shows the word « Carousel ». Add the
  labels to `src/i18n/admin/sections.ts`.

All of work item 3 is on branch `payload` (the builder's core, `src/fields/sections/`,
plus `grid.ts`): no schema change, so no migration, but run the skip-empty check anyway.
